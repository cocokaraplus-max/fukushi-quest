# FUKUSHI QUEST 326 — アプリ版（TASUKARU とは完全別）

イベント「FUKUSHI QUEST（福祉クエスト）」用の Web アプリ。
演出フル収録の最終デモを土台に、**PWA（スマホにアプリのように追加できる形）** へ整理したもの。
**TASUKARU（kaigo-ai-app）とはコード・データ・ホスティングを一切共有しない別アプリ。**

## ファイル構成
- `index.html` … 本体（ガチャ演出フル収録：プチュン／群予告／復活／大当たり／確率調整／景品／ハズレ。画像は base64 埋め込みで自己完結）
- `manifest.webmanifest` … PWA 設定（名前・アイコン・スタンドアロン表示）
- `service-worker.js` … オフラインキャッシュ（HTTPS/localhost で有効）
- `icons/` … アプリアイコン（192 / 512 / maskable）

## 動作確認（ローカル）

```

python3 -m http.server 8000
# ブラウザで http://localhost:8000/index.html
```

## 無料で公開する（お金をかけない）
このフォルダを**無料の静的ホスティング**にそのまま置くだけ（サーバー不要）。
- 例：Cloudflare Pages ／ GitHub Pages ／ Netlify（いずれも無料枠）
- 公開 URL（HTTPS）を **QR コード**にして会場で配布 → 参加者はスマホで開く
- PWA なので「ホーム画面に追加」でアプリのように使える（App Store 不要＝審査料 0 円）

## `fq-sw-v3` — Service Worker のキャッシュ（★これが一番危なかった）

**何が起きていたか。** v2 はすべての GET を「キャッシュ優先」で返していた。

1. Supabase の `ranking` / `prizes` の取得は **GET** なので、**最初の1回の結果が固定され、
   二度と更新されなかった。** ランキングも「在庫が減ると当たりにくくなる」仕組みも死ぬ。
2. `index.html` にも更新が届かない。**当日の朝に直しても、前日に開いた人には古い画面が出続ける。**

**どう直したか。**

- **別ドメイン（Supabase / supabase-js の CDN / Google Fonts）は一切さわらない＝素通し。**
  `url.origin !== self.location.origin` なら `respondWith` を呼ばずに抜ける。
- 同一オリジンの **HTML と `config.js` はネットワーク優先**。つながらない時だけキャッシュを出す
  （＝オフラインでも開ける、という PWA の利点は残る）。
- アイコン・manifest だけキャッシュ優先。
- キャッシュ名を `fq326-v2` → **`fq326-v3`** に変更。古い版は `activate` で捨てられる。

**★次にこのフォルダを直して公開する時は、`service-worker.js` の `CACHE` の数字を必ず上げること。**
v3 以降は HTML がネットワーク優先なので通常は不要だが、アイコンを差し替えた時などは要る。

## `fq-rank-lite-v1` — 1500人で無料枠が破綻する問題

**何が起きるはずだったか。** 参加者端末が `participants` の realtime を購読していたため、
**誰か1人がQRを読むたびに、会場の全端末がランキングを丸ごと取り直していた。**

- 1500人 × 7回スキャン ＝ 約1万回の更新イベント
- それが1500端末に飛び、1回あたり **97,854 バイト**（実測。1500人ぶんの全件）を再取得
- 掛け算になるので、転送量は理論上ペタ級。**Supabase 無料枠は月5GB。**
- そもそも **realtime の同時接続は無料枠200** なので、1500人は繋がりきらない

**開始30分で止まる。** 認識番号のかぶりより先に効いてくる問題だった。

**どう直したか。**

- **参加者端末の realtime 購読を廃止。** realtime は本部モニター（`honbu.html`）だけにする。
- ランキングは **上位20人＋自分の1行** だけ取る。2本の小さなクエリに分けた。
  - 上位: `.select('recog_no,nickname,points,rank').gt('points',0).order('rank').limit(20)`
  - 自分: `.select(...).eq('recog_no', DID).limit(1)`
  - 自分の順位は `ranking` ビューの `rank` 列をそのまま使う（以前は取ってきた全件から数えていた）
  - **実測 97,854 バイト → 1,261 バイト（約1/70）**
- 更新は **60秒ごと、かつ `document.visibilityState==='visible'` の間だけ**。
  画面を戻した時にも1回取る。ガチャ演出中（`window.busy`）は取りにいかない。
- `rankBusy` フラグで、前の取得が終わる前に重ねて投げない。

**見積り：** 1500端末 × 4時間 × 60秒ごと × 1.4KB ≒ **500MB**。無料枠5GBの1/10に収まる。
実際は画面を閉じている人が多いのでもっと少ない。

**★参加者端末に `sb.channel(...)` を足さないこと。** 人数ぶん掛け算になる。

## `fq-recog-serial-v1` — 認識番号のかぶり

**何が起きるはずだったか。** 端末が `1000〜9999` の乱数（9000通り）を自分で決めていた。
1500人だと**期待される衝突は125組**（誕生日のパラドックス）。
かぶった2人は `participants` の同じ行を共有するので、**ポイントも当選記録も混ざる。**
大抽選会はこの番号で当選を発表するので、そのままトラブルになる。

**どう直したか。**

- Supabase のシーケンスから連番を配る RPC **`issue_recog()`** を追加。`0001, 0002, …`。
  10000人を超えると自動で5桁になる（頭打ちしない）。**1500回発行して重複0を確認済み。**
- 端末は受け取った番号を `localStorage` に保存し、`fukushi_quest_326_did_srv='1'` を立てる。
  2回目以降の起動では**取り直さない**。
- **`issue_recog` はここでは `participants` に行を作らない。**
  「開いただけの人」を本部ランキングに出さないため。行は、なまえを入れるか
  最初のポイントが入った時点で `add_points` が作る。
- **★電波が悪くて発行できなかった端末**は、乱数のまま「**仮1234**」と表示して普通に動く
  （演出は止めない）。次に開いた時、まだ1ポイントも送っていなければ発行し直す。
  **すでに送っていたら番号を変えない**（変えると同じ人が2行に分かれるため）。
- 受付の職員へ：**「仮」が付いている人は番号が確定していない。**
  電波の良い場所で開き直してもらう。

## `fq-role-v1` — テストパネル・主催者設定を参加者から隠す

**何が起きていたか。** 「🧪 音・演出をすぐ確認」パネルと「⚙️ 主催者用の設定」が
**全参加者に見えていた。**

- 「➕ ポイント+1」を連打すれば、**会場を回らずにガチャが引ける**
- 「⚙️」から**当たる確率とレア度を書き換えられる**
- 「最初からやり直す」でガチャ回数がリセットされ、**何度でも引ける**

**どう直したか（URLで切り替え・端末に記憶）。**

| URL | 出るもの | 誰が使うか |
|---|---|---|
| `…/index.html` | 何も出ない | **参加者（既定）** |
| `…/index.html?dev=1` | 🧪テストパネル＋「最初からやり直す」 | 職員の動作確認用 |

| `?dev=0` / `?admin=0` | 消す | — |

**職員・主催者の端末は最初に1回だけこのURLで開けばよい。** 以後は普通のURLでも出る。

### あわせて：ガチャ回数の上限をサーバー側で固定した

そこで `claim_prize` の中で **`draws` の件数を数えて、1端末3回を超えたら必ず null（＝ハズレ）** を返す。
**回数を変えたい時は `supabase_migration_20260824.sql` の `MAX_DRAWS` の数字だけ変えて再度 Run。**

※ ローカル抽選のレア度（`_pickLv`）は端末側なので、書き換えれば特賞を狙い撃ちできる。
ただし**3回上限＋サーバー在庫**があるので、最悪でも1人が特賞3個まで。実害は限定的と判断した。
気になるならレア度もサーバーで決める作りに変えられる（未実装）。

## 触ると壊れる場所

1. **参加者端末（`index.html`）に `sb.channel(...)` を足さない。** 人数ぶん掛け算になって無料枠が飛ぶ。
2. **ランキングを `.select('*')`（全件）に戻さない。** 1回 97KB × 1500端末。
3. **Service Worker で別ドメインを `respondWith` しない。** ランキングと在庫が固定される。
4. **`claim_prize` に引数を足さない。** `create or replace` では置き換わらず**多重定義**になり、
   アプリからの2引数の呼び出しが「どちらの関数か曖昧」でエラーになる。
   回数を変えたいだけなら中の `MAX_DRAWS` を変える。
5. **`issue_recog` で `participants` に行を作らない。** 開いただけの人が本部ランキングに並ぶ。
6. **演出（`runFx` / `runLose` / `runSwarm` / `sfx` / `FX` / `<style>`）は正本。**
   直す時は、この6か所のハッシュが変わっていないことを確認してから渡すこと。

## `fq-draws3-v1` — ハズレ個数の自動計算が3倍ずれていた

主催者設定の「来場者数からハズレを自動計算」が、**1人1回引く前提**で
`ハズレ = 来場者数 − 景品合計` を計算していた。

**実際は1人が最大3回引ける。** 1500人なら**ガチャは最大4500回**。
1人1回で計算すると当たりが濃く出すぎて、**景品が全体の1/3あたりで尽きる**。
尽きたあとはサーバー在庫が0になり自動でハズレ演出になる（＝壊れはしない）が、
**後半に来た人が1つももらえない。**

直したこと：

- `DRAWS_PER_PERSON = 3` を定義し、`ハズレ = 来場者数 × 3 − 景品合計` に変更
- 合計欄に「想定来場者 N人 × 3回 ＝ ガチャ最大 M回」と、過不足を表示
- **景品が尽きる回数の目安**を赤字で警告（`⚠ この設定だと、景品は約 N 回目（全体の X%）で尽きます`）

**★この `3` は `supabase_migration_20260824.sql` の `MAX_DRAWS` と必ず同じ数にすること。**
片方だけ変えると、画面の確率と実際の挙動がずれる。

### 数の決め方（1500人の場合）

当たりは毎回 `景品合計 ÷ 全本数` の確率で抽選される（箱から減るのではない）。
景品はサーバー在庫なので、**当選が在庫数に達した時点で以後は全部ハズレ**になる。
つまり **在庫が尽きるのは、およそ「全本数」回目**。

- 景品を685個 用意 → **ハズレを 3815個以上**にすれば、全4500回のあいだ薄く広く当たり続ける
- ハズレを35個のままにすると、**最初の720回（全体の16%）で景品が尽きる**

`check.html` の④が、この計算をやって必要なハズレ個数を出してくれる。

## `fq-dev-gate-v1` — 開発パネルを、自分だけが出せるようにする

### これまでの問題

`?dev=1` を一度開くと、**その端末が「開発パネルを出す」と覚えていた。**

- URLさえ知っていれば誰でも出せた
- 一度出すと `?dev=0` で消すまで残った
- 貸し出す端末で消し忘れると、来場者に「ポイント+1」が見えてしまう

### これから — 条件が3つ「全部」

1. **URLに `?dev=1`（`?admin=1`）が付いている、そのときだけ。端末は何も覚えない。**
   付けずに開き直せば消えている。**`?dev=0` で消す作業は不要になった**
2. その端末が `fq_dev_devices` に登録されている
3. 合言葉（`dev_pass`）が合っている

### ★端末の登録は SQL Editor からだけ

アプリから登録できるようにすると、**合言葉を知った人が自分の端末を足せてしまう**ので、
わざと登録の口をアプリに作っていない。

**登録の手順**

1. 自分の端末で `https://cocokaraplus-max.github.io/fukushi-quest/?dev=1` を開く
2. 合言葉を入れて「確認」
3. 「この端末は登録されていません」と出て、**端末の番号**が表示される
4. その番号を `fq_dev_gate.sql` の一番下の登録用の行に貼り、**`--` を外して**その2行だけ Run
5. もう一度 `?dev=1` で開けばパネルが出る

**端末ごとに1回**必要（スマホとパソコンの両方で使うなら2回）。

### ★正直な限界

ブラウザで動くアプリなので、**本気で解析されれば防げない。**
目標は「**URLを教え合っただけでは絶対に出せない**」ところまで。会場に来るのは一般の方で、
開発者ツールで中身を書き換える人はまず居ない、という前提で線を引いている。

### ★通信できないと出ない

合言葉の照合が Supabase なので、**圏外や `config.js` 未設定ではパネルが出ない。**
安全側に倒してある。開発中に困ったら、そこを思い出すこと。

### 検証したこと（実際のブラウザで23項目・全通過）

URLに何も付けないと入口も出ない／`?dev=1` で入口だけ出る／
合言葉が違うと断り、**端末が登録済みかどうかも教えない**／
合言葉が合っても未登録の端末では出ず、端末の番号を表示／
登録済み＋正しい合言葉でパネルが出る／
**`?dev=1` なしで開き直すと消えている**（端末は何も覚えていない）／
`?admin=1` は主催者リンクだけ出す／**合言葉は画面のコードに入っていない**

SQLも実際の Postgres 16 で4通り確認（合言葉違い／未登録／両方OK／別端末）。

## `fq-logo-beat-v1` — ロゴが1文字ずつ鼓動する（2026-08-26）

### 何をしたか

「つながるフェスタ」のロゴが、**つ→な→が→る→フ→ェ→ス→タ** の順に、
心臓のように「ドクン・ドク」と大きくなって戻る。

- **1文字ずつ 0.5秒あけて**鼓動する
- **20秒にひとまわり。** つ から タ まで 4.4秒、そのあと約15秒は静か（＝時々）
- 鼓動は2拍。本物の心臓と同じで**2拍目は小さい**（16% → 7%）
- 動きが苦手な方の端末では鼓動しない（`prefers-reduced-motion`）

### ★どうやっているか（ここが要点）

**ロゴは絵なので、そのままでは1文字だけ動かせない。**
そこで **1文字ずつの絵に切り分けて、元と同じ位置に重ねている。**

切り方は**縦にスパッと切っていない。** それをやると、が と る のように
輪郭や影が重なっている所で、片方の黒フチが相手側へ持っていかれる。

代わりに **文字の色を手がかり**にした。

1. まず「つながっていない部分」を自動で見つける（つ／な／が＋る の3つに分かれた）
2. 残った「が＋る」は、**オレンジ**と**黄緑**の2色を種にする
3. 黒フチ・灰色の影は、**どちらの色に近いか**で振り分ける

結果、8枚を重ね直すと**元の絵と1画素も違わない**ことを確認した。

### ★止まっているときの見た目

**今までと同じ。** ただし厳密には、**輪郭のにじみ方だけが1画素ぶん変わる。**
1枚の絵を960px→226pxに縮めるのと、8枚を別々に縮めるのとで、
輪郭の計算がわずかに違うため。

実測：平均の差 **4/255（1.6%）**、違いが出るのは**輪郭の線の上だけ**。
拡大して並べても目では区別できなかった。

### 絵の大きさ

8枚あわせて **40KB**（今までの2枚は38KB）。**表示は重くならない。**
色数を64色に減らして保存しているが、**元の絵との差はゼロ**（測って確認）。
ロゴは色数が少ないので、減色しても1画素も変わらない。

### ★数字を変えたいとき

`@keyframes lg-beat` の近くにある3つだけ触ればよい。

| | |
|---|---|
| `20s` | ひとまわりの長さ。長くすると「たまにしか動かない」 |
| `.5s` | 文字と文字のずれ。大きくすると波がゆっくり流れる |
| `1.16` | どれだけ大きくなるか（16%）。1.10 でも十分わかる |

★**`20s` を変えたら `@keyframes` の％も計算し直すこと。**
`1.2%` は「ひとまわりの1.2%」＝20秒なら0.24秒。
0.24秒・0.46秒・0.64秒・0.9秒 になるよう％を合わせる。

★`left` / `top` / `width` の％は**絵の中での位置**。手で書き換えると文字がズレる。
**絵を作り直したときだけ測り直す。**

### 残件・注意

- 表示に使う絵が2枚から8枚に増えたので、**1枚でも読み込みに失敗するとその文字だけ消える。**
  （今までも logo_line1.png が失敗すれば「つながる」が丸ごと消えたので、
  危険が増えたというより形が変わった。）
- **元の `logo_line1.png` / `logo_line2.png` は消していない。** 戻したいとき用。
- キャラクターの絵（頭が切れていない版）への差し替えは**まだ**。別作業。

### 次に同じことがあったときの調べ方

「止まっているときの見た目が変わっていないか」を目で判断しない。
同じ場所のスクリーンショットを2枚取って、差を数字で出す。

```python

from PIL import Image
a = np.array(Image.open('before.png').convert('RGB'), int)
b = np.array(Image.open('after.png').convert('RGB'), int)
d = np.abs(a - b)
print(d.mean(), d.max())      # 平均が数以下で、違いが輪郭だけなら合格
```

## `fq-cast-v4` — 歩く子が透明になっていた件ほか（2026-08-26）

### ★★① 歩く子がだんだん透明になっていた（私のミス）

**症状**：箱の顔の子（326さん）が、歩いているあいだに少しずつ薄くなっていく。

**原因**：`fq-cast-v3` でコマを書き直したとき、
**途中のコマから「濃さ(opacity)」の指定を落とした。**

```css
 0.5%  {opacity:1; …}   ← ここで「濃い」
 1%    {           …}   ← 濃さの指定なし
16.5%  {           …}   ← 濃さの指定なし
33.3%  {opacity:0; …}   ← ここで「消える」
```

**CSSは、指定のあるコマとコマのあいだを自動でなめらかにつなぐ。**
だから「0.5%で濃い → 33.3%で消える」を、
**歩いている20秒かけてじわじわ薄くしていた。**

実測（直す前）:

```
3秒=0.86  6秒=0.71  9秒=0.56  12秒=0.41  15秒=0.25  18秒=0.10
```

直したあとは 3秒〜18秒まですべて **1.00**。

**★教訓：ひとつの動きの中で opacity を使うなら、どのコマにも書く。**
1コマでも抜くと、そこは「間を取ってなめらかにつなぐ」対象になる。

★もとの書き方（`1%,92% {opacity:1;}` のように opacity 専用のコマを分ける）
なら抜けにくい。**コマをまとめて書き直すときが危ない。**

### ★同じ穴が他にないか、機械的に調べた

```python
import re
s = open('index.html', encoding='utf-8').read()
for m in re.finditer(r'@keyframes (a-[a-z]+)\{(.*?)\n  \}', s, re.S):
    frames = [l for l in m.group(2).split('\n') if '{' in l and '%' in l]
    n_op = sum(1 for l in frames if 'opacity' in l)
    if n_op != len(frames):
        print('★', m.group(1), n_op, '/', len(frames))
```

結果：**抜けがあったのは `a-walk` だけ**。他の8つは全コマに入っていた。
このコードはパッチの検算にも組み込んである（`歩く子の全コマに濃さの指定 : 7 / 7`）。

### ② 緑の子（走る）をゆっくりに

追い抜きは **13.05秒**、画面の右から4割の位置（実測）。

★**これ以上のばすと、15.1秒に出てくる黒猫と重なって3人になる。**
`a-dash` の `3.8%` がその上限に近い。

### ③ 着地のゆれを強く

| | 前 | 後 |
|---|---|---|
| いちばん大きなずれ | 7px | **13px** |

| 収まるまで | 0.48秒 | **0.70秒** |

## `326.png` が透けていた件（2026-08-26）

### 何が起きたか

箱の顔の子（326さん）が、**うしろのカウントダウンや背景の文字が透けて見える**状態だった。
`fq-cast-v5` で「まえ」に出したことで、はじめて気づいた。
（うしろにいたときは、透けていても後ろが何もないので分からなかった。）

### 原因は2つ重なっていた

**① 元の `326.png` が、白い所ごと透明になっていた**

背景を「明るい色は消す」という方法でぬいたため、
**キャラクターの中の白い部分まで一緒に消えていた。**

```
絵の中の alpha（0=透明 / 255=不透明）の分布
    1〜 63 : 17.0%   ← 白い顔・腕・脚の部分
  250〜254 : 74.9%
     255   :  0.0%   ← 完全に不透明な画素が1つも無い
```

★これは `ch_◯◯.png` を作るときに気をつけた点と同じ穴。
**「明るさで消す」のではなく「画像のふちからつながっている白だけ」を消す。**

**② ★色数を減らす処理が、透明度まで壊していた**

さらに悪いことに、私が軽量化のためにかけた
`Image.quantize(colors=256, method=FASTOCTREE)` が、**透明度を色と一緒に混ぜてしまった。**

```
色を減らす前 : 完全に不透明 42.0%  絵の中の平均 200
色を減らした後: 完全に不透明  0.0%  絵の中の平均 144  ← 半分近く透けている
```

**★理由**：パレット形式のPNGは「色＋透明度」を1組で持つ。
中間の透明度がたくさんあると、量子化がそれらを近い色どうしでまとめてしまい、
**中身まで半透明の色に置き換わる。**

### やったこと

1. いったん**白い紙の上に置き直す**（元の紙の上での見た目に戻す）
2. **ふちからつながっている「うすい所」だけ**を背景とみなし、内側の穴も埋める
3. **透明度を「0か255だけ」にする**（中間値を作らない）
4. そのうえで色数を減らす

```python
hard = ((a >= 128) * 255).astype('uint8')      # ★ここが肝。中間値を残さない
out  = Image.fromarray(np.dstack([rgb, hard]), 'RGBA')
q    = out.quantize(colors=192, method=Image.FASTOCTREE, dither=Image.NONE)
```

結果：**中身の平均 alpha 255（完全に不透明）／48,339バイト → 26,156バイト**。
色のずれは平均0.3・最大18で、見た目は変わらない。

### ★他の9枚は無事だった（確認済み）

同じ量子化をかけた `ch_◯◯.png` 9枚も調べたが、
**中身（ふちの2pxを除く）の平均 alpha は 254〜255** で問題なし。

326.png だけ壊れたのは、**もともと中間の透明度が大量にあった**ため。
中間値が少ない画像なら、量子化しても混ざらない。

### 残件

- なし（326.png は差し替え済み）

### 次に同じことがあったときの調べ方

**「透けている気がする」と思ったら、赤い紙の上に置いてみる。** 一発で分かる。

```python
from PIL import Image
i = Image.open('img/326.png').convert('RGBA')
bg = Image.new('RGBA', i.size, (220,20,20,255))
bg.alpha_composite(i)
bg.convert('RGB').save('check.png')     # 赤が透けて見えたら、そこが透明
```

数字で確かめるなら、**ふちを除いた「中身」の alpha を見る**。

```python
import numpy as np
from scipy import ndimage
b = np.array(Image.open('img/326.png').convert('RGBA'))[:,:,3]
core = ndimage.binary_erosion(b > 0, iterations=3)
print(b[core].mean(), b[core].min())     # 255 に近ければ不透明
```

★**画像を軽くしたら、必ずこの検査をすること。** 軽さだけ見て透明度を見ないと、
今回のように「軽くなったが透けた」を見逃す。

## `fq-cast-v6` — 透けた箱の顔を外し、みどりの子が散歩を引き継ぐ（2026-08-26 夕方）

`326.png` はパレット形式のPNGで、透明度が 0 か 255 の2つしかない。

絵を作り直すのではなく、**この子をキャラクターの列から外した。**
代わりに、それまで「高速で走って追い抜く役」だった**みどりの子が散歩を引き継ぐ。**

`a-walk` の `scaleX` だけを入れ替えたもので、**2つで1組。**

**「絵が透けている」と思ったとき**

`index.html` の `actors:` のすぐ上にある**時間割の表を必ず数え直す。**

## `fq-logo-daku-v2` — v1 が「る」の壁を引き連れていた（2026-08-26 夜・v1の直後）

### 何が起きたか

`fq-logo-daku-v1` を公開したあと、**「が」が鼓動するたびに「る」の壁（3Dの側面の灰色）が
一緒についてくる**のが見つかった。濁点は直ったが、**別の所を壊していた。**

★README に何度も書いている **「直した直後に別の所が壊れる」** が、また起きた。

### 原因

v1 は「**濁点の芯までの距離 ＜ 「る」の芯までの距離**」で1画素ずつ振り分けていた。
この決め方には2つの穴があった。

**穴①：灰色の壁を途中で切る。**
壁は1枚の面なのに、距離で決めると**面の真ん中に境目が来る。**
半分が「が」に、半分が「る」に付いて、鼓動のたびに壁が裂ける。

**穴②：距離は「見た目の持ち主」と一致しない。**
問題の面は `x770-840 y63-85` にある細長い灰色で、
**「る」の腕の真下**にある＝どう見ても「る」の壁。
ところが「る」の緑はそこから右上に離れているため、
**距離で測ると濁点のほうが近い。** それで濁点のものにされていた。

★**近さは、持ち主を決める根拠にならない。**
2度目の試みで「面の大多数の画素がどちらに近いか」に変えたが、**同じ理由で失敗した。**
（この面は、大多数の画素も濁点のほうが近い。）

### やったこと

考え方を変えた。**黒い輪郭線を「仕切り」とみなして、絵を「面」に分ける。**
面とは、黒で囲まれたひとつながりの色の領域（文字の色、壁の灰色）のこと。
そして**面ごと丸ごと**どちらかに振り分ける。**面を途中で切らない。**

どの面がどちらのものかは、**絵を見て名指しで決めた**（数が少ないので確実）。

| 面（画素数と枠） | 正体 | 持ち主 |
|---|---|---|
| 295 / `x751-768 y17-46` | 濁点2画目の本体（オレンジ） | 濁点 |
| 318 / `x727-746 y25-56` | 濁点1画目の本体（オレンジ） | 濁点 |
| 519 / `x766-786 y19-82` | 濁点2画目の壁（うすい灰） | 濁点 |
| 155 / `x752-772 y55-71` | 濁点の下の壁 | 濁点 |
| 60 / `x741-750 y64-75` | 濁点1画目の下の壁 | 濁点 |
| **887 / `x770-840 y63-85`** | **「る」の腕の真下の壁** | **「る」** ← v1 はここを間違えた |

黒い輪郭線は、**いちばん近い面の持ち主**にした。
その結果、濁点と「る」のあいだの黒い帯（6〜7画素）は、**半分ずつ**に分かれる。
どちらの文字にも自分の輪郭線が残るので、鼓動しても線が消えない。

★スクリプトは面を**画素数と枠でぴったり指定**している。
絵を作り直すと合わなくなるが、そのときは**何も書かずに止まる**（`need()`）。
黙って別の面を掴むことはない。

| | v1 | v2 |
|---|---|---|
| `lg_ga.png` | width 27.2917% ／ 262×245 ／ 7,754B | **width 26.7708%** ／ 257×245 ／ 7,695B |
| `lg_ru.png` | left 79.5833% ／ width 20.4167% ／ 196×250 ／ 4,536B | 同左 ／ 196×250 ／ 4,551B |

`index.html` で変わったのは **「が」の width の1つだけ**。

★**検算**

- 4枚を重ね直して、**元の1枚絵との差 0画素**
- 濁点の本体1,347画素が **1,347画素とも「が」の絵**に入っている
- **「る」の壁887画素のうち、「が」の絵に入ったのは 0画素**
- 「が」の絵に「る」の緑は **0画素**
- 行ごとに「が」の右端」と「るの緑の左端」を並べ、あいだが黒だけであることを確認

### ★公開のときにやったこと（絵を差し替えたときは必ず要る）

`service-worker.js` の `CACHE` を **`fq326-v4` → `fq326-v5`** に上げた。

**なぜ要るか。** `service-worker.js` は **HTML はネットワーク優先**だが、
**画像は「キャッシュ優先」**（69行目あたり）。
一度端末に取り込まれた絵は、**キャッシュ名を変えない限り、いつまでも古いまま出続ける。**

★**HTMLだけを直したときは不要。絵を差し替えたときは必ず要る。**
（この使い分けは README の `fq-sw-v3` の節にも書いてある。）

### 残件

なし。★`fq-logo-daku-v1` の節に書いた「残件なし」は**誤り**だった（この不具合が残っていた）。

### 次に同じことがあったときの調べ方

**絵を2つに切り分けるときの原則**

★**距離で決めない。面で決める。**
輪郭線で囲まれたひとつながりの色（＝面）を最小単位にして、**面を割らない。**
面を割ると、鼓動・拡大のたびにそこが裂けて見える。

★**面の持ち主は「近さ」では決まらない。**
3Dの壁は、本体から離れた場所まで伸びる。
**絵を見て決めるのがいちばん確実。** 面の数はたいてい10もない。

★**名指しで決めたら、画素数と枠で照合して、合わなければ止める。**
絵を作り直したときに、黙って別の面を掴むのを防ぐ。

**確認のしかた**

1. 2枚を別々に並べて表示し、**それぞれが単独で成立しているか**を見る
2. 行ごとに「片方の右端」と「もう片方の左端」を並べ、**あいだに何があるか**を見る
   （黒い輪郭線だけなら正常。灰色が挟まっていたら壁を割っている）
3. 重ね直して**元の1枚絵との差が0画素**であることを確認する

★1と2は別のことを見ている。**3（差0）は、切り分けが正しいことを保証しない。**
どこで切っても差は0になる。**差0は「画素を落としていない」ことしか言っていない。**
