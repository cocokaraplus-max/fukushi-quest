# FUKUSHI QUEST 326 — アプリ版（TASUKARU とは完全別）

イベント「FUKUSHI QUEST（福祉クエスト）」用の Web アプリ。
演出フル収録の最終デモを土台に、**PWA（スマホにアプリのように追加できる形）** へ整理したもの。
**TASUKARU（kaigo-ai-app）とはコード・データ・ホスティングを一切共有しない別アプリ。**

## ファイル構成
- `index.html` … 本体（ガチャ演出フル収録：プチュン／群予告／復活／大当たり／確率調整／景品／ハズレ。画像は base64 埋め込みで自己完結）
- `manifest.webmanifest` … PWA 設定（名前・アイコン・スタンドアロン表示）
- `service-worker.js` … オフラインキャッシュ（HTTPS/localhost で有効）
- `icons/` … アプリアイコン（192 / 512 / maskable）

## 動作確認（ローカル）
`file://` で直接開くと Service Worker が無効になるため、簡易サーバーで開く：
```
cd fukushi-quest-app
python3 -m http.server 8000
# ブラウザで http://localhost:8000/index.html
```

## 無料で公開する（お金をかけない）
このフォルダを**無料の静的ホスティング**にそのまま置くだけ（サーバー不要）。
- 例：Cloudflare Pages ／ GitHub Pages ／ Netlify（いずれも無料枠）
- 公開 URL（HTTPS）を **QR コード**にして会場で配布 → 参加者はスマホで開く
- PWA なので「ホーム画面に追加」でアプリのように使える（App Store 不要＝審査料 0 円）

## `fq-sw-v3` — Service Worker のキャッシュ（★これが一番危なかった）

**何が起きていたか。** v2 はすべての GET を「キャッシュ優先」で返していた。

1. Supabase の `ranking` / `prizes` の取得は **GET** なので、**最初の1回の結果が固定され、
   二度と更新されなかった。** ランキングも「在庫が減ると当たりにくくなる」仕組みも死ぬ。
2. `index.html` にも更新が届かない。**当日の朝に直しても、前日に開いた人には古い画面が出続ける。**

**どう直したか。**

- **別ドメイン（Supabase / supabase-js の CDN / Google Fonts）は一切さわらない＝素通し。**
  `url.origin !== self.location.origin` なら `respondWith` を呼ばずに抜ける。
- 同一オリジンの **HTML と `config.js` はネットワーク優先**。つながらない時だけキャッシュを出す
  （＝オフラインでも開ける、という PWA の利点は残る）。
- アイコン・manifest だけキャッシュ優先。
- キャッシュ名を `fq326-v2` → **`fq326-v3`** に変更。古い版は `activate` で捨てられる。

**★次にこのフォルダを直して公開する時は、`service-worker.js` の `CACHE` の数字を必ず上げること。**
v3 以降は HTML がネットワーク優先なので通常は不要だが、アイコンを差し替えた時などは要る。

## `fq-rank-lite-v1` — 1500人で無料枠が破綻する問題

**何が起きるはずだったか。** 参加者端末が `participants` の realtime を購読していたため、
**誰か1人がQRを読むたびに、会場の全端末がランキングを丸ごと取り直していた。**

- 1500人 × 7回スキャン ＝ 約1万回の更新イベント
- それが1500端末に飛び、1回あたり **97,854 バイト**（実測。1500人ぶんの全件）を再取得
- 掛け算になるので、転送量は理論上ペタ級。**Supabase 無料枠は月5GB。**
- そもそも **realtime の同時接続は無料枠200** なので、1500人は繋がりきらない

**開始30分で止まる。** 認識番号のかぶりより先に効いてくる問題だった。

**どう直したか。**

- **参加者端末の realtime 購読を廃止。** realtime は本部モニター（`honbu.html`）だけにする。
- ランキングは **上位20人＋自分の1行** だけ取る。2本の小さなクエリに分けた。
  - 上位: `.select('recog_no,nickname,points,rank').gt('points',0).order('rank').limit(20)`
  - 自分: `.select(...).eq('recog_no', DID).limit(1)`
  - 自分の順位は `ranking` ビューの `rank` 列をそのまま使う（以前は取ってきた全件から数えていた）
  - **実測 97,854 バイト → 1,261 バイト（約1/70）**
- 更新は **60秒ごと、かつ `document.visibilityState==='visible'` の間だけ**。
  画面を戻した時にも1回取る。ガチャ演出中（`window.busy`）は取りにいかない。
- `rankBusy` フラグで、前の取得が終わる前に重ねて投げない。

**見積り：** 1500端末 × 4時間 × 60秒ごと × 1.4KB ≒ **500MB**。無料枠5GBの1/10に収まる。
実際は画面を閉じている人が多いのでもっと少ない。

**★参加者端末に `sb.channel(...)` を足さないこと。** 人数ぶん掛け算になる。

## `fq-recog-serial-v1` — 認識番号のかぶり

**何が起きるはずだったか。** 端末が `1000〜9999` の乱数（9000通り）を自分で決めていた。
1500人だと**期待される衝突は125組**（誕生日のパラドックス）。
かぶった2人は `participants` の同じ行を共有するので、**ポイントも当選記録も混ざる。**
大抽選会はこの番号で当選を発表するので、そのままトラブルになる。

**どう直したか。**

- Supabase のシーケンスから連番を配る RPC **`issue_recog()`** を追加。`0001, 0002, …`。
  10000人を超えると自動で5桁になる（頭打ちしない）。**1500回発行して重複0を確認済み。**
- 端末は受け取った番号を `localStorage` に保存し、`fukushi_quest_326_did_srv='1'` を立てる。
  2回目以降の起動では**取り直さない**。
- **`issue_recog` はここでは `participants` に行を作らない。**
  「開いただけの人」を本部ランキングに出さないため。行は、なまえを入れるか
  最初のポイントが入った時点で `add_points` が作る。
- **★電波が悪くて発行できなかった端末**は、乱数のまま「**仮1234**」と表示して普通に動く
  （演出は止めない）。次に開いた時、まだ1ポイントも送っていなければ発行し直す。
  **すでに送っていたら番号を変えない**（変えると同じ人が2行に分かれるため）。
- 受付の職員へ：**「仮」が付いている人は番号が確定していない。**
  電波の良い場所で開き直してもらう。

## `fq-role-v1` — テストパネル・主催者設定を参加者から隠す

**何が起きていたか。** 「🧪 音・演出をすぐ確認」パネルと「⚙️ 主催者用の設定」が
**全参加者に見えていた。**

- 「➕ ポイント+1」を連打すれば、**会場を回らずにガチャが引ける**
- 「⚙️」から**当たる確率とレア度を書き換えられる**
- 「最初からやり直す」でガチャ回数がリセットされ、**何度でも引ける**

**どう直したか（URLで切り替え・端末に記憶）。**

| URL | 出るもの | 誰が使うか |
|---|---|---|
| `…/index.html` | 何も出ない | **参加者（既定）** |
| `…/index.html?dev=1` | 🧪テストパネル＋「最初からやり直す」 | 職員の動作確認用 |
| `…/index.html?admin=1` | ⚙️主催者用の設定 | 主催者の端末 |
| `?dev=0` / `?admin=0` | 消す | — |

一度開けば `localStorage`（`fukushi_quest_326_role`）に記憶されるので、
**職員・主催者の端末は最初に1回だけこのURLで開けばよい。** 以後は普通のURLでも出る。

### あわせて：ガチャ回数の上限をサーバー側で固定した

画面を隠しても、`localStorage` を書き換えられる人には効かない。
そこで `claim_prize` の中で **`draws` の件数を数えて、1端末3回を超えたら必ず null（＝ハズレ）** を返す。
**回数を変えたい時は `supabase_migration_20260824.sql` の `MAX_DRAWS` の数字だけ変えて再度 Run。**

※ ローカル抽選のレア度（`_pickLv`）は端末側なので、書き換えれば特賞を狙い撃ちできる。
ただし**3回上限＋サーバー在庫**があるので、最悪でも1人が特賞3個まで。実害は限定的と判断した。
気になるならレア度もサーバーで決める作りに変えられる（未実装）。

## 触ると壊れる場所

1. **参加者端末（`index.html`）に `sb.channel(...)` を足さない。** 人数ぶん掛け算になって無料枠が飛ぶ。
2. **ランキングを `.select('*')`（全件）に戻さない。** 1回 97KB × 1500端末。
3. **Service Worker で別ドメインを `respondWith` しない。** ランキングと在庫が固定される。
4. **`claim_prize` に引数を足さない。** `create or replace` では置き換わらず**多重定義**になり、
   アプリからの2引数の呼び出しが「どちらの関数か曖昧」でエラーになる。
   回数を変えたいだけなら中の `MAX_DRAWS` を変える。
5. **`issue_recog` で `participants` に行を作らない。** 開いただけの人が本部ランキングに並ぶ。
6. **演出（`runFx` / `runLose` / `runSwarm` / `sfx` / `FX` / `<style>`）は正本。**
   直す時は、この6か所のハッシュが変わっていないことを確認してから渡すこと。

## `fq-draws3-v1` — ハズレ個数の自動計算が3倍ずれていた

主催者設定の「来場者数からハズレを自動計算」が、**1人1回引く前提**で
`ハズレ = 来場者数 − 景品合計` を計算していた。

**実際は1人が最大3回引ける。** 1500人なら**ガチャは最大4500回**。
1人1回で計算すると当たりが濃く出すぎて、**景品が全体の1/3あたりで尽きる**。
尽きたあとはサーバー在庫が0になり自動でハズレ演出になる（＝壊れはしない）が、
**後半に来た人が1つももらえない。**

直したこと：

- `DRAWS_PER_PERSON = 3` を定義し、`ハズレ = 来場者数 × 3 − 景品合計` に変更
- 合計欄に「想定来場者 N人 × 3回 ＝ ガチャ最大 M回」と、過不足を表示
- **景品が尽きる回数の目安**を赤字で警告（`⚠ この設定だと、景品は約 N 回目（全体の X%）で尽きます`）

**★この `3` は `supabase_migration_20260824.sql` の `MAX_DRAWS` と必ず同じ数にすること。**
片方だけ変えると、画面の確率と実際の挙動がずれる。

### 数の決め方（1500人の場合）

当たりは毎回 `景品合計 ÷ 全本数` の確率で抽選される（箱から減るのではない）。
景品はサーバー在庫なので、**当選が在庫数に達した時点で以後は全部ハズレ**になる。
つまり **在庫が尽きるのは、およそ「全本数」回目**。

- 景品を685個 用意 → **ハズレを 3815個以上**にすれば、全4500回のあいだ薄く広く当たり続ける
- ハズレを35個のままにすると、**最初の720回（全体の16%）で景品が尽きる**

`check.html` の④が、この計算をやって必要なハズレ個数を出してくれる。

## 公開のしかた（GitHub Pages）

このフォルダは `https://github.com/cocokaraplus-max/fukushi-quest.git` の `main` につながっている。
**サーバーは要らない。静的ファイルを置くだけ。**


そのあと GitHub の **Settings → Pages** で
**Source: Deploy from a branch** ／ **Branch: main ／ (root)** → **Save**。
数分待つと公開される：

| ページ | URL |
|---|---|

**★リポジトリが Private だと、無料プランでは Pages が使えない。**
その場合は Public にするか、Cloudflare Pages（フォルダをドラッグするだけ・無料）を使う。

### `config.js` を公開リポジトリに置いてよいか

**よい。** anon public キーは「ブラウザに配るためのキー」で、
アプリを開いた人は誰でも読める（＝公開が前提）。書き込みは
`security definer` の関数（`add_points` / `claim_prize` / `issue_recog`）と RLS で守られている。
**service_role キーは絶対に置かないこと。** こちらは全権限を持つ。

## `fq-flat-v1` — 枠の傾きをやめた

元のデザインは、`section` を1つおきに **±0.4度** 傾けていた。
「手で貼った紙」の風合いを出すための演出（背景の紙色・破線の枠・手書き風フォントとセット）。

```css
/* 元のCSS。いまはコメントアウトしてある */
section:nth-of-type(odd){transform:rotate(-.4deg);}
section:nth-of-type(even){transform:rotate(.4deg);}
```

**2026-08-24 にユーザー判断で外した。** 理由は2つ。

1. 見ていて落ち着かない（本人の言葉：「なんか気持ち悪い」）
2. 傾いた要素の中の文字は、端末によって輪郭がぼやける。
   **1500人がそれぞれ違う端末で見るので、読みやすさを優先した**

**★この2行は消さずに `<style>` の中にコメントとして残してある。** 戻したくなったらコメントを外すだけ。

**★これは `<style>`（＝演出の正本）に手を入れた唯一の箇所。**
「演出は触っていない」という確認をするときは、この1か所だけ差分が出るのが正しい。

`honbu.html` と `check.html` はもともと傾いていない（遠くから数字を読む画面なので）。
